### B. Practice-advance pure logic (W2) — NEW `src/lib/practice-advance.ts`

Frozen API implemented verbatim: `TopicStat` + `computeTopicStats(attempts)`; `ReviseEntry` + `buildReviseQueue(attempts)`; `buildAdaptiveSet({bank, topicStats, count, seed})`. Pure functions, no localStorage/JSX/`"use client"`; type-only imports from `./tracking`/`./data`; the only value import is `hashSeed`/`mulberry32` from `./data`. Semantics (each pinned by suite checks):

- `computeTopicStats`: MCQ-only (kind quiz/mock; flash excluded even with itemRecords); aggregates `ItemRecord.topic` with first-pass `correct`; empty/blank-topic records skipped; attempts without `itemRecords` contribute nothing (documented limitation: pre-tracking attempts never appear); `attempts` = attempts contributing ≥ 1 record to the topic; `lastAnsweredAt` = max record `answeredAt`, null when all null; sort accuracy ASC → total DESC → topic ASC; accuracy unrounded `(correct/total)*100` (same convention as `computeStats`; callers round for display).
- `buildReviseQueue`: attempts ordered by `date` ASC (stable), records in array order, last record per questionId wins; entry iff the latest record has `correct === false` (clearing rule: a later correct first-pass answer removes the question; a later wrong one re-enters it); unanswered records (`correct === false`) DO enter; `wrongCount` = all wrong records for the qid; `lastWrongAt` = `date` of the attempt holding the latest wrong record; `lastAnsweredAt` = max `answeredAt` across all records for the qid; output lastWrongAt DESC (nulls last) → questionId ASC. The queue is DERIVED from stored attempts on every load — no new localStorage key; it survives reload because attempts persist, and a question clears only when a submitted re-answer records a correct first pass.
- `buildAdaptiveSet`: weight `1 + 2*(1 − accuracy/100)` for topics with total ≥ 3, else 1 (unseen topics still appear); weighted lottery without replacement via `mulberry32(hashSeed(seed))`; empty `topicStats` (or empty bank) → uniform shuffle with the same RNG; count clamped [0, bank.length]; deterministic given the same inputs; inputs never mutated; same question object references returned. The no-history fallback re-implements the `shuffled()` Fisher-Yates loop inline (byte-equal to the real `shuffled()`, pinned 3 seeds × 5 counts) because the frozen import list allows value imports from `./data` only for `hashSeed`/`mulberry32`. Existing fixed/seeded mock sampling is untouched — this function is used only by the adaptive practice entry point.

Coordinator-confirmed interpretation (W2 §2b.4, BRIEF silent): `buildReviseQueue` does NOT skip blank-topic records — the empty-topic rule appears only under `computeTopicStats`, the queue is keyed by questionId, and skipping would break clearing. Pinned by an explicit test.

## 3. P1 per-subject practice resume — DESIGN ONLY (NOT implemented; owner approval required before any implementation)

**Status: design for owner approval. No code in this batch implements it. The one-active-session behaviour in the deployed code is EXACTLY as today.**

**The gap, precisely.** `src/lib/practice.ts` persists ONE object under `etea_practice_state_next`: `{subjectKey, round, seed}`. The QuizRunner sessions themselves are per-scope and DO persist (an old subject's stored session stays stored), but the round/seed pointer for the old subject is overwritten when the user switches subjects — so returning to it builds a fresh set (round 0, fresh seed) instead of rebuilding the identical set that would match the stored session's fingerprint and offer Resume. What is lost is the pointer, not the session.

**Proposed shape (versioned map, same key).**

```ts
// v2 shape, stored under the SAME key "etea_practice_state_next":
{ version: 2, lastSubject: string, entries: { [subjectKey: string]: { round: number; seed: number } } }
```

- `entries` holds one `{round, seed}` per subject the user has practiced. `lastSubject` records the most recently active subject so the Home Start-here resume link keeps working (it reads the stored state to offer Continue).
- The practice page reads ONLY its own subject's entry and writes ONLY its own entry (read-modify-write of the map; never overwrite the whole map with a single entry).
- `resolvePracticeInitial` gains the map: a param naming a valid subject restores THAT subject's entry when present, else starts fresh (round 0, fresh seed); the bare URL restores `lastSubject`'s entry. The current same-subject-restore semantics are preserved as the single-entry case.

**Migration (preserves the existing single session).** On first read, if the stored value parses as the OLD single-object shape (string `subjectKey` + numeric `round`/`seed`, no `version` field), convert it to `{version: 2, lastSubject: <subjectKey>, entries: { [<subjectKey>]: {round, seed} }}` and write the v2 shape back. The existing session's pointer is preserved as that subject's entry — nothing is lost, nothing is re-seeded. If the value is already v2, use as-is. If it is unparseable, fall back to a fresh state (today's fail-safe behaviour, unchanged). The old-shape reader stays in the code as a permanent fallback (cheap, fail-safe); the old key is never deleted — the migration writes the v2 shape to the SAME key only after a successful parse of the old shape.

**Fail-safe behaviour.** The QuizRunner session fingerprint/compatibility guard is untouched: a stale or mismatched session still offers Start fresh and never applies stale answers. If two subjects' entries ever collide or corrupt, the affected subject degrades to a fresh set; other subjects are unaffected. Backup export/import: the practice-state key is not part of the backup export today (it is device-local UI state); this design does not change that. No new localStorage key is introduced.

**Tests required before deploy (when approved).** Old-shape migration preserves round/seed exactly; two subjects coexist (write for A does not clobber B's entry); invalid stored JSON → fresh state; bare URL restores `lastSubject`; a param naming a stored subject restores its entry; fingerprint still rejects stale sessions (existing suite); Home resume link still resolves. Estimated scope: `practice.ts` (load/resolve/migrate) + practice page read/write sites + Home resume read + one new suite. No QuizRunner, tracking, or bank changes.

**Owner decision needed:** approve this design (implement in a later batch) or keep the one-active-pointer behaviour. Until the owner approves, no implementation work will be done.
